# Proposal: "Berthline" — Pragmatic MVP dock scheduler

**Angle:** Pragmatic MVP. Ship a working, boring, well-explained system in the first 3 Baron-hours (CRUD + conflict + fit checks + import + tests + README), then spend the remaining time on one extra that makes the 23 years of data do the talking. Risk-averse, minimal dependencies, every assumption written down. Uniqueness comes from the honesty of the write-up, not from the pixel count.

## Pitch

Berthline replaces the dockmaster's eyeball check with two rules a reviewer can read in one screen: a vessel must be shorter than its berth, and on any given day the vessels on a berth must add up (with clearance) to no more than the berth's length. It is a Python + SQLite + Flask app with a vanilla-JS grid that looks like the spreadsheet the facility already uses, so nobody has to relearn anything. The importer turns 23 years of messy grids into rows with a source cell reference on every booking and a ledger of every ambiguity it could not resolve, and the audit page runs today's rules over yesterday's data so the reviewer can see real double-bookings and misfits the old process let through. Everything runs from `pip install -r requirements.txt` and two commands; there is no build step, no framework magic, and no number in the database that the code invented.

## Stack (and why)

| Layer | Choice | Why this and not the alternative |
|---|---|---|
| Language | Python 3.12 (Homebrew) | Already in the install plan; most readable language for a beginner to explain; club lists Python-style backends. |
| Storage | SQLite via stdlib `sqlite3` | Zero install, one file, real SQL date-range queries, and "database" is a thing the club builds. A JSON file would need hand-written range queries; Postgres needs a server. The `.db` is gitignored and regenerated by the importer. |
| Import | `openpyxl` (pip) | The importer must see merged ranges and fill colors, which csv export loses. It is the only non-trivial dependency and is used by the importer only, never by the app. |
| Web | Flask (pip) | A 60-line `app.py` a beginner can read top to bottom. Stdlib `http.server` would double the code for routing and JSON. FastAPI adds pydantic and async concepts Baron cannot yet explain. |
| Frontend | One `static/index.html` + `app.js`, vanilla JS, no build | The brief prefers it; the UI is one grid and one form; a bundler would be the riskiest install on this machine. |
| Tests | `pytest` (pip) | Plain `assert` reads better in an interview than `self.assertEqual`. One install. |
| Hosting | Reviewer runs locally (`python app.py`) | Guaranteed to work; GitHub Pages cannot run Flask. A static read-only snapshot for Pages is the first thing cut (see out_of_scope). |

Installs required: Homebrew, `brew install python@3.12 gh`, then `python3.12 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt` (openpyxl, flask, pytest). Nothing else.

## Architecture

```
dock-scheduler/
  README.md                 what it is, how to run, DECISIONS, ASSUMPTIONS, known limits
  requirements.txt          openpyxl, flask, pytest
  app.py                    Flask routes only; every route is "parse JSON -> call dock.* -> return JSON"
  dock/
    __init__.py
    models.py               dataclasses Berth, Vessel, Booking, Finding (pure Python, no DB)
    rules.py                fit_check(), capacity_check(), check_booking(), suggest_berths(), audit()
    db.py                   schema (SQL string), connect(), row<->dataclass helpers, queries
    classify.py             classify(cell_text) -> (kind, canonical_name, type_prefix)
    importer.py             workbook -> berths, vessels, bookings, import_issues; prints a report
  static/
    index.html, app.js, style.css   month grid, booking form, findings panel, Audit tab, Issues tab
  tests/
    test_rules.py, test_classify.py, test_importer.py, test_api.py
  data/
    Dock Schedule - Synthetic Sample.xlsx   (the input, committed)
  docs/
    import_report.md        generated by the importer; committed so reviewers see it without running
```

Data flow: `importer.py` reads the workbook once and writes `dock.db`. `app.py` opens `dock.db` per request. Every mutation (POST /api/bookings) calls `rules.check_booking()` first and refuses to save when any finding has severity `error`, unless the body carries an `override_reason`. The frontend never computes rules; it only renders `Finding` objects returned by the API, so the UI and the audit page show identical messages for identical situations. `rules.py` imports nothing but `datetime` and `models.py`, which is what makes it unit-testable in isolation and explainable in isolation.

### Endpoints

| Method, path | Purpose |
|---|---|
| GET `/api/berths` | list berths with length and capacity_mode |
| GET `/api/vessels`, POST `/api/vessels`, PATCH `/api/vessels/<id>` | list, create, fix a length |
| GET `/api/bookings?year=&month=` (optional `berth_id`) | bookings covering that month, for the grid |
| POST `/api/check` | body = candidate booking; returns findings, saves nothing |
| POST `/api/bookings` | same body; 201 on success, 409 with findings when any error and no `override_reason` |
| DELETE `/api/bookings/<id>` | remove |
| GET `/api/suggest?vessel_id=&start=&end=` | berths ranked for this stay |
| GET `/api/audit?year=` | findings from running the rules over every stored booking of that year |
| GET `/api/issues?kind=` | the importer's ambiguity ledger |

## Data model

- **berths**(id, name UNIQUE, length_ft NULL, capacity_mode ∈ {`linear`,`single`,`unchecked`}, notes). Invariant: `single` and `linear` require length_ft; `unchecked` is for group rows the grid gives no length for ("North Finger Piers:", "Small craft slips") and skips capacity rules. Seeded from the grid labels: North Pier West 410 linear, North Pier Face 75 single, North Pier East 240 linear, Inner Channel 55 single, South Float West 90 single, South Float East 90 single. Reason for `single` below 100 ft: two vessels plus 10 ft clearance on a 75–90 ft float is implausible and the registry's smallest yachts are 24 ft, so a per-berth mode is clearer than a magic threshold; the mode is a column, so staff can flip a float to `linear` without a code change.
- **vessels**(id, name, name_key UNIQUE, type_prefix, length_ft NULL, length_source ∈ {`registry`,`manual`,NULL}, notes). name_key = prefix + name, lowercased, punctuation stripped, `OS/V`→`OSV`, so "Barge SALT DORY" and "Barge Salt Dory" are one row. Registry length conflicts (R/V High Reef 32' vs 72', M/V Deep Reef 24' vs 100') store NULL plus an issue rather than guessing.
- **bookings**(id, berth_id, vessel_id NULL, kind ∈ {`vessel`,`event`,`closure`}, title, start_date, end_date, status ∈ {`confirmed`,`override`}, override_reason NULL, source ∈ {`import`,`manual`}, source_ref e.g. `2013!AH12`, span_source ∈ {`merged`,`repeat`,`fill`,`single`,`manual`}, notes). Invariants: start_date ≤ end_date; kind=`vessel` ⇔ vessel_id not NULL; index on (berth_id, start_date, end_date).
- **import_issues**(id, sheet, cell, raw_value, kind, decision, booking_id NULL). kind ∈ {`note_skipped`,`span_ambiguous`,`header_year_mismatch`,`day_count_mismatch`,`unknown_berth_label`,`unclassified_value`,`length_conflict`,`joined_across_month`,`summary_mismatch`}.

Time semantics: **dates only, end-inclusive**. A stay written across cells 3, 4, 5 is `start=03, end=05`, which is how the grid already thinks and what staff would type. Two bookings overlap iff `a.start <= b.end and b.start <= a.end`. There are no hours: "Departs 0600 / ETA 1200" same-day turnovers are not modelled; a shared day counts as shared (assumption 4).

## Algorithms

**Fit check** `fit_check(vessel, berth) -> Finding|None`. If berth.capacity_mode == `unchecked` → None. If vessel.length_ft is None → warning `length_unknown` ("cannot verify fit; add a length to the vessel"). If vessel.length_ft > berth.length_ft → error `does_not_fit`. O(1).

**Capacity check** `capacity_check(candidate, existing, berth, clearance_ft=10) -> list[Finding]`. `existing` = bookings on the same berth whose range overlaps the candidate's (one indexed SQL query). For each day D in the candidate's range:
1. S = candidate ∪ {b in existing covering D}.
2. If any b in S has kind `closure` (and it is not the candidate itself) → error `berth_closed` on D.
3. If any b in S has kind `event` and |S| > 1 → error `event_occupies_berth` on D (a community sail day takes the whole berth; this is the simplest rule that matches the brief's "events also occupy a berth").
4. Else if capacity_mode == `single`: |S| > 1 → error `double_booked` on D, listing the other bookings.
5. Else if `linear`: known = lengths of vessels in S with a length; load = sum(known) + clearance_ft × (|S| − 1). If load > berth.length_ft → error `capacity_exceeded` on D with the arithmetic in the message ("120 + 145 + 10 = 275 > 240"). If any vessel in S has no length and no error → warning `capacity_unverified` on D.
6. `unchecked` → nothing.
Consecutive days with the same finding are collapsed into one Finding with a date range so the UI shows "Jun 3–7: capacity exceeded" not five lines. Complexity O(days × |S|); the candidate range is days long and |S| is rarely above 4, so the naive loop is the right choice. The full audit calls the same function per stored booking against its own overlaps and de-duplicates by (berth, day, code); 2,600 bookings × ~5 days each is about 15,000 day checks, well under a second, so a sweep line was written down as the known optimisation and not implemented (interview point 6).

**check_booking** = fit_check + capacity_check + `berth_inactive` warning if the berth has no bookings at all in that decade (cheap proxy for "this berth may not have existed then"; berths have no active dates in the grid).

**Suggest** `suggest_berths(vessel, start, end)`: run check_booking against every berth; drop berths with errors; sort by (number of warnings, berth.length_ft ascending). Smallest-fit-first keeps the 410 ft face free for the ships that need it. Returns the findings alongside each candidate so the UI can say why a berth is second.

Edge cases handled in tests: adjacent ranges (Jan 1–3 vs Jan 4–6) do not overlap; same-day single-day booking; candidate that is itself a closure (blocks nothing retroactively but is reported against existing bookings as `closure_over_existing` warning); vessel with unknown length on a single-mode berth alone (no finding); editing a booking excludes its own id from `existing`.

## Importer

`python -m dock.importer data/"Dock Schedule - Synthetic Sample.xlsx"` drops and recreates `dock.db`, then writes `docs/import_report.md`. It is deterministic and idempotent, so the reviewer's run reproduces the committed report byte-for-byte.

Per year sheet (1997–2019), per month block:
1. **Header row**: column A matches a month name (`JANUARY 1999`, `January`). Year: if the month is December and it is the first block on the sheet, year = sheet_year − 1 (sheets that start with the previous December); otherwise year = sheet_year. If the header carries a year that differs from that (the 2010 sheet's "NOVEMBER 2018"/"DECEMBER 2018"), the sheet name wins and an issue `header_year_mismatch` is logged. Reason: the sheet name was typed once; block headers were copy-pasted.
2. **Day-1 column**: the first cell equal to literal `1` in the header row or the two rows below it; day N is day-1 column + N − 1. The other day cells are `=SUM(B3+1)` formulas with no cached values, so counting columns is the only option. If the count of consecutive numeric/formula cells ≠ days in that month → `day_count_mismatch` (parse continues with the calendar's count).
3. **Berth rows**: column A matches `^(North Pier|Inner Channel|South Float|North Finger|Small craft)`; the label is split into name and optional `NN'` length. Group rows become `unchecked` berths. Any other non-empty column A inside a block → `unknown_berth_label`, row skipped.
4. **Cell classification** (`classify.py`, ported from the taxonomy already built): starts with a type prefix (R/V, M/V, F/V, S/V, M/Y, S/Y, OSV/OS/V, Tug, Barge, USCG) → `vessel`, title-cased, prefix canonicalised; exact match in a 27-entry override table → `event`/`closure`/`note` with a canonical label; ETA/ETD/Departs/Fueling/Bunkering/Delayed/Touch and go patterns → `note`; anything else → imported as `event` with `unclassified_value` so no data is silently dropped. Notes are **not bookings**: they go to import_issues as `note_skipped`, and if a booking on the same berth covers that day the note text is appended to that booking's notes ("Fueling @0800"). "Bunker barge" is a vessel booking with no registry entry; "Fuel truck" is a note.
5. **Span**: merged cell → span = merged columns (`merged`, 2009+). Else the same value repeated in the following cells → run (`repeat`). Else the cell has a non-default fill and the following cells carry the same fill until a blank fill or a different value → run (`fill`). Else one day (`single`) and, for sheets before 2009, `span_ambiguous` is logged because a single filled cell in those years may mean a longer stay. The report states how many bookings came from each span_source; that number is the honest error bar on every pre-2009 statistic.
6. **Month boundary**: after a sheet is parsed, a booking ending on the last day of a month is joined with one for the same vessel on the same berth starting on day 1 of the next month (`joined_across_month`). Year boundaries are joined the same way after all sheets load.
7. **Registry** (Science, Yachts): a row starts a vessel when its first cell has a type prefix and ends in `NN'`; `LOA: NN'` cells on a named vessel are recorded in notes, not used as length (the name's length is what staff typed on the schedule side too). Conflicting lengths → NULL + `length_conflict`. Vessels seen only in the grid get a row with NULL length; the report lists how many grid vessels have a known length (about 19 of 504, so most fit checks will be warnings, and the README says so up front).
8. **8YR Dock Summary**: not imported as bookings. Used as a cross-check: usage-days per berth per year computed from imported bookings for 2006–2013 are printed next to the sheet's numbers, differences logged as `summary_mismatch` and left unexplained where they are (the summary has Marsh Landing and North Finger Piers, which the grids barely do). Tours: skipped, they are point-in-time visits that do not occupy a berth.

Every booking keeps `source_ref` (`2013!AH12`) so any number in the app can be traced to a cell in the file the facility already trusts.

## Unique features (ranked; cost = Baron-hours; the first is the "one extra")

1. **Historical audit page** — run today's rules over all 23 years and list every double-booking and misfit with its source cell. Why it impresses: it answers "does it work?" on the client's own data instead of a toy example, and each hit is falsifiable by opening the spreadsheet at that cell. Cost 0.5. Depends on importer + rules.
2. **Berth load strip** — for a chosen berth and month, a row of day cells shaded by load ÷ length (linear berths) or occupied/free (single), with the arithmetic on hover. This is the smallest honest version of Baron's "diagram of boats and berths": it visualises the exact quantity the rule checks, nothing more. Cost 0.5. Depends on audit endpoint.
3. **Ambiguity ledger in the UI** (Issues tab) — the importer's issues table with filters; reviewers see that the system knows what it does not know. Cost 0.25. Depends on importer.
4. **Summary cross-check** — the 8YR sheet vs recomputed usage-days, as a table in the import report. Cost 0.25. Depends on importer.
5. **Override with reason** — an error can be saved with `override_reason`; the audit shows overrides separately. The system advises, the dockmaster decides (rafting exists). Cost 0.1, included in core.
6. **GitHub Pages read-only snapshot** — `index.html` falls back to `docs/demo.json` when the API is absent. Cost 0.25. First thing cut.

## Risks

1. Fill-colour span detection behaves differently per era (0.5 h sink). Mitigation: time-box to 20 minutes; fall back to `single` + `span_ambiguous` and say so in the report. The system is still correct; only the historical statistics get wider error bars.
2. Baron cannot explain code he did not type. Mitigation: Phase 7 is protected; every phase has "must explain" items; README Decisions are written by Baron, not generated.
3. Homebrew/Python install eats the buffer. Mitigation: start Phase 0 the evening before; Phases 1–2 need only Python.
4. Reviewer's machine lacks Python 3.12. Mitigation: code uses nothing newer than 3.10 syntax; README says "3.10+".
5. Synthetic data has an unseen layout quirk in one era. Mitigation: importer never raises on one bad block; it logs `unknown_berth_label`/`day_count_mismatch` and continues, so a surprise costs a row of the report, not the demo.
6. Temptation to build the animation. Mitigation: the load strip is the agreed ceiling; anything beyond goes in README "Next steps".

## Assumptions

1. A booking is measured in whole days, end-inclusive; two bookings sharing a calendar day share the berth that day.
2. Berth lengths in the row labels are the only berth facts; there are no depths, tides or drafts in scope.
3. On long piers (410', 240') vessels berth end to end and the constraint is linear: sum of lengths + 10 ft clearance between neighbours ≤ berth length; the 10 ft is a named constant, not a fact from the client.
4. Same-day turnovers ("Departs 0600" then "ETA 1200") are not modelled; they appear as a shared day and, on single berths, as a conflict the dockmaster can override with a reason.
5. Berths under 100 ft hold one vessel at a time (`single` mode); rafting alongside is not modelled.
6. Non-vessel events and closures occupy the whole berth for their dates.
7. Operational notes (ETA, fueling, weather) are annotations, not reservations, and are attached to the booking they sit on.
8. The sheet name is the authoritative year; a December block at the top of a sheet belongs to the previous year.
9. Vessel identity is the normalised name; two names within edit distance 2 (R/V Quiet Tern vs R/V Quiet Heron) are distinct vessels unless staff merge them.
10. Registry lengths are the only source of vessel length; conflicting registry lengths mean "unknown" until a person fixes it in the UI.
11. Group rows ("North Finger Piers:", "Small craft slips") have unknown capacity and are exempt from checks.
12. Pre-2009 single filled cells with no fill run are one-day stays, flagged ambiguous.
13. The 8YR Dock Summary is an independent report, not source data; disagreements are reported, not reconciled.
14. Single user, trusted network, no authentication; the facility runs it on one machine.

## Interview points

1. **Why is a booking end-inclusive days rather than datetimes?** The client's artefact is a grid with one cell per day; a stay across cells 3–5 is naturally "3 to 5". Datetimes would force me to invent arrival and departure hours the data does not contain (the ETA/Departs notes are the exception, not the rule). Whole days keep the overlap test to one line and mean every statistic can be checked against the sheet by counting cells. The cost is that same-day turnovers look like conflicts, which I surface as overridable errors rather than hide.
2. **What exactly is a conflict?** For one berth and one day: a closure blocks everything; an event blocks everything else; on a single-vessel berth any second booking is a conflict; on a linear berth the known lengths plus 10 ft clearance per gap must not exceed the berth length. Unknown lengths produce a warning ("unverified"), never a silent pass or a fake fail. That rule is `capacity_check()` in `rules.py`, about 30 lines, covered by six tests.
3. **Why not treat unknown length as full berth or as zero?** Both are lies. Zero makes the check pass and teaches staff to trust a green light that means nothing; full-berth makes every unknown yacht block a 410 ft pier. A warning with the instruction "add a length" pushes the fix to the one place it belongs, the vessel record, and the fit check turns real the moment it is filled in.
4. **How did you import 23 years of inconsistent sheets?** By writing down a ladder of evidence for each cell and keeping the rung on the row: merged range, repeated name, matching fill run, or single cell. Anything below "merged" on a pre-2009 sheet is flagged ambiguous. The year comes from the sheet name because block headers were copy-pasted (2010 says "NOVEMBER 2018"). Nothing is dropped: values I could not classify become events with an issue, and notes are attached to the booking they annotate. The importer's output is a report the reviewer can diff.
5. **What did you get wrong on purpose?** Rafting, drafts, tides and hours. Each would have needed a number the client never gave me; I documented them as assumptions and made the override-with-reason path so the dockmaster is never blocked by my ignorance.
6. **What is the complexity, and why did you not optimise it?** Checking one booking is O(days × overlapping bookings), a few dozen operations. The full audit is about 15,000 day checks and runs in well under a second. A sweep line would be O(n log n) and harder to read; with 2,600 bookings, readable wins. I wrote the optimisation down instead of implementing it.
7. **Why Flask + SQLite + vanilla JS?** Fewest concepts per line. The reviewer can read `app.py` in two minutes, `rules.py` has no imports beyond datetime, and the browser only renders what the API says, so the UI cannot disagree with the audit. A framework would have added a build step on a machine that did not have Node, and I would have been explaining Webpack instead of berths.
8. **How do you know it works on the real data?** The audit runs the same function the booking form uses over every imported booking and lists hits with a cell reference; I opened several in the workbook and they are real double-bookings under my rules. The 8YR summary sheet is recomputed from imported bookings and the differences are printed, including the ones I cannot explain (Marsh Landing is in the summary but hardly in the grids). The tests cover the rules and the importer's edge cases with a synthetic mini-workbook, and a smoke test on the real file.
