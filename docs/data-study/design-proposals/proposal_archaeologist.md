# Proposal: Dock Ledger (angle: Data archaeologist)

## name
Dock Ledger - "23 years of berths, audited"

## angle
Data archaeologist. The 23-year workbook is the star: an importer reads every layout era, records every ambiguity as a first-class row, reconciles the result against the facility's own 8YR summary, and produces a data-quality report that proves the problem with the client's own history. The app is then the tool that prevents those mistakes going forward, with the legacy data loaded and browsable and every booking traceable to the cell it came from.

## pitch
Every applicant will build a form that rejects a double-booking. Dock Ledger first turns the facility's real 23-year spreadsheet into structured reservations, then runs the same conflict and fit rules over that history and reports: "your own schedule contains N days where a berth was over capacity, M vessels assigned to berths they cannot fit, K mislabelled month headers, J stays whose length had to be guessed, and the 8YR summary disagrees with the grids in these cells". The rules that produce that report are the exact same 60 lines of Python that guard the booking form, so the report is both the argument for the product and its integration test. Everything is Python 3.12 + SQLite + vanilla HTML/JS; a static export of the history and the audit is published on GitHub Pages so the reviewer sees the evidence before they run anything.

## stack
- Python 3.12 via Homebrew (`brew install python@3.12 gh`), because the brief defaults to Python and openpyxl is the only mature library that reads merged-cell ranges and cell fills, which the pre-2009 span inference needs.
- openpyxl (pip): reads .xlsx including `ws.merged_cells.ranges`, `cell.fill`, and cached formula values (`data_only=True`) for the 1997-2003 day rows that are `=SUM(B3+1)` formulas.
- sqlite3 (stdlib): zero install, a real relational schema Baron can show in an interview, a single `dockledger.db` file the reviewer can open with any SQLite viewer; foreign keys and a CHECK constraint carry the invariants.
- FastAPI + uvicorn (pip): one `api.py`, type-hinted request models Baron can read, and the free `/docs` page lets a reviewer call `POST /api/check` without the UI. Flask would save one install but loses `/docs` and validation.
- pytest (pip): the fit/capacity rules get named test cases the interviewer can read as a spec.
- Frontend: vanilla HTML/CSS/JS, no build step; one `index.html`, one `app.js` that draws the timeline as inline SVG. Reason: the reviewer must be able to open the repo and read it; nothing to compile; GitHub Pages serves it directly.
- Hosting: GitHub Pages serves `site/` (read-only history + audit report from exported JSON). The write path (create a reservation) runs locally with `uvicorn`, three commands in the README. Reason: Pages cannot run Python and I refuse to duplicate the rules in JS (single source of truth is an interview answer).
- Installs required, in order: Homebrew; `brew install python@3.12 gh`; `python3.12 -m venv .venv && source .venv/bin/activate`; `pip install openpyxl fastapi uvicorn pytest` (pinned in `requirements.txt`); `gh auth login`.

Data flow: `importer.py` (xlsx -> rows) -> `db.py` (SQLite) -> `audit.py` + `reconcile.py` (rules over history -> report) -> `export_static.py` (JSON for Pages). At runtime `api.py` reads/writes SQLite and calls `rules.find_conflicts()` for every `POST /api/check` and `POST /api/reservations`. The UI talks only to `/api/*` (local) or to `site/data/*.json` (Pages); `app.js` picks the source by probing `/api/berths` once at load.

Endpoints (`api.py`):
- `GET /api/berths` -> berths with length_ft, capacity_mode, active years.
- `GET /api/vessels?q=` -> name search with length_ft and length_source.
- `GET /api/reservations?from=&to=&berth_id=` -> reservations overlapping the window, each with `source_ref` (e.g. `2012!C41:H41`).
- `GET /api/load?berth_id=&from=&to=` -> per-day list `{date, feet_used, feet_capacity, n_vessels, status}` for the timeline bar.
- `POST /api/check` body `{berth_id, vessel_id|label, kind, start_date, end_date}` -> `{ok, findings:[{severity, code, message, day, details}]}`; never writes.
- `POST /api/reservations` same body -> 201 with the row, or 422 with the same findings if any severity is `error`. Warnings do not block.
- `DELETE /api/reservations/{id}` (only rows with `source='app'`; imported history is read-only, reason: the audit must stay reproducible).
- `GET /api/issues?code=&year=` and `GET /api/audit` -> the report as JSON.
- `GET /docs` free from FastAPI.

## data_model
SQLite `schema.sql`:
- `berths(id, name UNIQUE, length_ft INT, capacity_mode TEXT CHECK IN ('linear','single'), first_year, last_year, notes)`. Seed: the six labelled berths (410, 75, 240, 55, 90, 90); `North Finger Piers` and `Small craft slips` and `Marsh Landing` with length NULL and `capacity_mode='single'` because the grid gives no length. Rule: 75' and below or unknown -> `single`; otherwise `linear`.
- `vessels(id, name TEXT UNIQUE, type_prefix TEXT, length_ft INT NULL, length_source TEXT CHECK IN ('registry','manual','unknown'), draft_ft INT NULL, rafts_ok INT DEFAULT 0, registry_ref TEXT, notes)`. `name` is the normalized form (canonical prefix + Title Case), so "Barge SALT DORY" and "Barge Salt Dory" are one row.
- `reservations(id, berth_id FK NULL, vessel_id FK NULL, kind TEXT CHECK IN ('vessel','event','closure'), label TEXT, start_date TEXT, end_date TEXT, source TEXT CHECK IN ('import','app'), source_ref TEXT, span_confidence TEXT CHECK IN ('merged','repeated','fill','single','app'), created_at, CHECK(end_date >= start_date), CHECK(kind!='vessel' OR vessel_id IS NOT NULL))`. `berth_id NULL` means "waterfront-wide" (closures found in unlabelled rows).
- `annotations(id, berth_id NULL, date TEXT, text TEXT, source_ref TEXT)`: operational notes ("ETA 1200", "Fuel truck"); shown on the timeline, never counted in capacity.
- `issues(id, code TEXT, severity TEXT CHECK IN ('info','warning','error'), sheet TEXT, cell_ref TEXT, raw_value TEXT, message TEXT, resolution TEXT, reservation_id FK NULL)`: every ambiguity the importer resolved and how. Codes: `MISLABELLED_HEADER, PREV_DECEMBER_BLOCK, SPAN_INFERRED_REPEATED, SPAN_INFERRED_FILL, CROSS_MONTH_JOINED, UNLABELLED_ROW, OUT_OF_GRID_CELL, HEADER_CORRUPTION, UNKNOWN_VESSEL_LENGTH, REGISTRY_LENGTH_CONFLICT, CASE_VARIANT_MERGED, NOTE_NOT_BOOKING, SUMMARY_MISMATCH, SUMMARY_BERTH_NOT_IN_GRID`.
- `audit_findings(id, code CHECK IN ('OVER_CAPACITY','DOES_NOT_FIT','CLOSURE_VIOLATED','UNVERIFIABLE'), berth_id, date, details_json)`: output of running `rules.find_conflicts()` over the imported history; regenerated by `audit.py`.

Time semantics: whole days, ISO `YYYY-MM-DD` strings (SQLite compares them correctly), `end_date` inclusive, because the grid is one column per day and has no arrival/departure times except in free-text notes. A reservation occupies every day in `[start_date, end_date]`; two reservations overlap iff `a.start <= b.end AND b.start <= a.end`. Year comes from the sheet name, never from the header text (invariant that fixes the 2010 "2018" labels).

## algorithms
`rules.py`, all pure functions, no database access (so tests need no fixtures and `audit.py` and `api.py` call the same code):

1. `fit_check(vessel, berth) -> Finding|None`: if `berth.length_ft` and `vessel.length_ft` are both known and `vessel.length_ft > berth.length_ft` -> `error DOES_NOT_FIT` ("145' R/V Clear Strand cannot fit 55' Inner Channel"). If `vessel.length_ft` is None -> `warning UNVERIFIABLE`. O(1).
2. `day_loads(reservations, berth, day_range) -> list[DayLoad]`: for each day, collect reservations covering it. `feet_used = sum(known lengths) + CLEARANCE_FT * (n_vessels - 1)` with `CLEARANCE_FT = 10` (a named constant with a comment: fenders and lines; chosen, not measured). `status`: `closed` if any covering reservation is `kind='closure'`; `event` if any is `kind='event'`; else `over` if (linear and feet_used > berth.length_ft) or (single and n_vessels > 1); else `unverifiable` if any covering vessel has unknown length; else `ok`. O(days x reservations) with a pre-filter by date range; 23 years x 8 berths x ~3 bookings/day is trivial.
3. `find_conflicts(candidate, existing, berth) -> list[Finding]`: run `fit_check`, then `day_loads` over `[candidate.start, candidate.end]` with `existing + [candidate]` (excluding `candidate.id` when editing). Emit one finding per day whose status is `over`/`closed`/`event`-with-vessel, plus one `warning UNVERIFIABLE` if any day is unverifiable. Severity rules: `DOES_NOT_FIT` error; `OVER_CAPACITY` error; `CLOSURE_VIOLATED` error; vessel added on an event day error (events occupy the berth per the brief); `UNVERIFIABLE` warning (unknown length never blocks, because most historic vessels have no length and blocking would make the tool unusable; the warning tells the coordinator to fill the length in).
4. Edge cases with named tests: end-inclusive overlap on the shared day; adjacent stays (1-5 and 6-7) do not overlap; equal length fits; sum exactly equal to berth length fits; single-mode berth rejects a second vessel of any length; a vessel booked on a closure day errors; editing a reservation excludes itself; unknown-length vessel on a full berth still warns rather than errors and the message says why.
5. Suggestion logic (`suggest_berths(candidate)`, cheap): run `find_conflicts` against every active berth for the same dates and return the ones with no errors, sorted by slack feet ascending (tightest fit first, keeps the 410' pier free for big ships). O(berths x days).
6. Audit = `find_conflicts` applied to each imported vessel reservation against the other imported reservations on its berth; findings are deduplicated per (berth, day) and stored in `audit_findings`. Because the same function is used, "the app would have caught this" is literally true.

## importer
`importer.py` runs sheet by sheet, `python -m dockledger.importer data/"Dock Schedule - Synthetic Sample.xlsx" dockledger.db`, and prints a one-line summary per year plus the issue counts.

Per sheet (year = int(sheet title)):
1. Find month header rows: column A matches `^(January|...|December)\b` case-insensitively. Era is not hard-coded; it is detected per block from what is found: (a) day numbers in the header row itself (2004+), or (b) in the row below, starting with `1` followed by `=SUM(..+1)` formulas (1997-2003). openpyxl is opened twice: `data_only=True` for cached values, `data_only=False` to see formulas; if a cached value is missing, day n is column `d1col + n - 1` (the formulas are strictly +1 per column, so position is the truth).
2. Month/year: month from the header text; year always from the sheet name. If header year != sheet year -> issue `MISLABELLED_HEADER` (this is what the 2010 "NOVEMBER 2018"/"DECEMBER 2018" blocks produce). If the first block is December and the sheet year is Y -> assign year Y-1 and issue `PREV_DECEMBER_BLOCK`; if that stay also exists in sheet Y-1 the duplicate is dropped and noted.
3. Berth rows: column A matches `^(North Pier|Inner Channel|South Float|North Finger|Small craft|Marsh Landing)`; length parsed from a trailing `NNN'`. Rows between the header and the next header that have values but no label -> every non-empty cell goes to `annotations` (or a `closure` with `berth_id NULL` if the taxonomy says closure), with issue `UNLABELLED_ROW`. Group rows like "North Finger Piers:" become a berth of their own with unknown length and `single` mode.
4. Cell classification via `taxonomy.py` (ported from the already-validated taxonomy in the analysis: 532 raw vessel strings -> 504 normalized names; 18 notes, 13 events, 10 closures; zero unclassified). Vessel prefixes: R/V, M/V, F/V, S/V, M/Y, S/Y, OSV (also OS/V), Tug, Barge, USCG(C). Notes ("ETA 1200", "Departs 0600", "Fueling @0800", "Fuel truck", "Delayed due to weather", "Touch and go") become `annotations` with issue `NOTE_NOT_BOOKING`, never reservations. "Bunker barge" is a vessel booking with an unnamed vessel row (it occupies the berth). "Emergency port call" is an event (occupies the berth, no vessel identity). "Holiday" and "Road race - access limited" are events that do not occupy a berth for capacity purposes (flag `exclusive=0` on the label table) - decision recorded in ASSUMPTIONS.
5. Spans, in priority order: (a) the cell is the top-left of a merged range -> one stay over the range, `span_confidence='merged'` (2009+); (b) the same normalized value appears in consecutive day columns of the same row -> one stay, `span_confidence='repeated'`, issue `SPAN_INFERRED_REPEATED` (1997-2008, e.g. "M/Y GREEN LANTERN" x4 in Jan 2006); (c) the named cell has a non-default fill and adjacent empty cells to the right share that fill -> extend, `span_confidence='fill'`, issue `SPAN_INFERRED_FILL`; (d) otherwise a one-day stay, `span_confidence='single'`. Rule (c) is implemented last and cut first if time runs out; the audit reports counts per confidence so the reader knows how much is inferred.
6. Cross-month joins: after a sheet is read, a stay ending on the last day of a month is joined with a stay of the same vessel and berth starting on day 1 of the next month -> one reservation with `source_ref` listing both ranges, issue `CROSS_MONTH_JOINED`. Same rule across the December/January sheet boundary.
7. Cells outside the day columns of a berth row (the 2010 November/December blocks have vessel names inside the header rows and left of day 1) -> issue `HEADER_CORRUPTION` or `OUT_OF_GRID_CELL` with the raw text; not imported as bookings. Honest rather than clever: the report lists them for a human.
8. Registry (`registry.py`): parse Science and Yachts sheets, fold continuation rows (phone/email fragments) into the vessel above, extract length from trailing `NN'` or `LOA: NN'`, record `rafts_ok` from "Will raft alongside", `short_visit`. Duplicates with conflicting lengths (R/V High Reef 32' vs 72', M/V Deep Reef 24' vs 100') get the maximum with issue `REGISTRY_LENGTH_CONFLICT` (conservative for fit checks; the report says so). Vessels seen in the grid but absent from the registry get `length_source='unknown'` and one `UNKNOWN_VESSEL_LENGTH` issue each (expected: most of the 504).
9. Reconciliation (`reconcile.py`): for 2006-2013 compute per berth per year `vessel_days` = sum of days over vessel reservations (the summary's 648 for North Pier West 2012 exceeds 366, so it counts vessel-days, not occupied days) and `occupied_days` = distinct days with any vessel; compare both to the 8YR sheet; store the delta as `SUMMARY_MISMATCH` (info if |delta| <= 5%, warning otherwise). "Marsh Landing" and "North Finger Piers" rows that have no grid row in those years -> `SUMMARY_BERTH_NOT_IN_GRID`. The expected outcome is disagreement; the point is to show the facility that its summary and its grid are not derived from each other.
10. Tours sheet: imported into `annotations` (date from Excel serial, headcount, vessel) only if time allows; otherwise listed in out_of_scope. It contains no berth bookings.

Idempotence: the importer deletes all `source='import'` rows and re-inserts, so re-running is safe and the audit is reproducible; app-created rows survive.

## unique_features
1. Data-quality report on the client's own history (`docs/DATA_QUALITY_REPORT.md` + Audit tab). What: headline counts (over-capacity days, does-not-fit assignments, mislabelled headers, inferred spans, unknown lengths, summary mismatches) each linking to the offending cells. Why it impresses: it proves the problem exists in their data before selling the fix, and it demonstrates that the rules engine works on 2,600 real bookings rather than 3 demo rows. Cost: 0.75 h. Depends on importer + rules.
2. Provenance on every booking. What: `source_ref` like `2012!C41:H41` shown when a reservation is clicked, plus the raw cell text and the issue that was recorded. Why: the coordinator can verify any claim the report makes against the workbook; reviewers love traceability. Cost: 0.25 h. Depends on importer.
3. 8YR summary reconciliation. What: a table berth x year with grid-computed vs summary-stated usage days and the delta. Why: nobody else will notice the summary sheet exists; it shows reading the whole workbook, not just the grids. Cost: 0.5 h. Depends on importer.
4. Linear-load timeline with proportional boats (Baron's animation wish, done cheaply). What: for one berth and month, an SVG row per day showing stacked rectangles whose widths are vessel lengths against the berth length, red when the sum exceeds it, a play button that steps through days. Why: it makes "410 feet holds several vessels end to end" visible and makes the capacity rule self-explanatory. Cost: 0.5 h (SVG rects, no library). Depends on `/api/load`.
5. Dry-run check endpoint (`POST /api/check`) plus `suggest_berths`. What: the form shows findings live as the user types, and offers the tightest berth that has no errors. Why: prevention instead of rejection. Cost: 0.25 h. Depends on rules.
6. Confidence-labelled spans. What: every imported stay says whether its length in days is `merged`, `repeated`, `fill` or `single`. Why: honest about the pre-2009 ambiguity and gives a number ("38% of pre-2009 stays are inferred") that no other applicant will have. Cost: included in importer.
7. Same rules, same tests, both directions. What: `tests/test_rules.py` is written as a readable spec and the audit uses the same function. Why: "how do you know it works" has a one-sentence answer. Cost: included in phase 2.

## risks
- Importer time overrun on span inference: mitigation is the priority order (merged -> repeated -> single first; fill-based last and cut first). The audit stays honest because confidence is recorded.
- openpyxl returns `None` for 1997-2003 formula cells if the file has no cached values: fallback is positional (day n = d1col + n - 1), tested in the fixture.
- The 2010 corrupted blocks resist parsing: they are reported as `HEADER_CORRUPTION` with raw text; not fixing them is the correct behavior for an audit tool.
- Summary reconciliation disagrees wildly: expected; the report frames it as a finding, and the vessel-days vs occupied-days comparison shows which definition the summary used.
- Baron cannot explain regexes or openpyxl merged-range code in the interview: mitigation is Phase 1 (see the data first) and the comment-per-rule style in `importer.py`; each ambiguity rule is a small function with the issue code in its name.
- Homebrew install takes long on a fresh Mac: start it first and read the data while it runs.
- Synthetic data may contain no true over-capacity day: then the headline reads "0 double-bookings, but 38% of stays are inferred and N vessels have unknown length, so the grid cannot prove it" - still a finding.

## assumptions
1. A reservation occupies whole days, end-inclusive, because the grid has one column per day and no times.
2. The year of a block is the sheet's year, never the header's text.
3. Berth length is the number in the row label; a berth of 75' or less, or of unknown length, holds one vessel at a time (`single`); longer berths are linear (`sum of lengths + 10' clearance per gap <= berth length`).
4. Clearance is 10 feet between rafted-in-line vessels; a named constant, chosen not measured.
5. Vessel lengths come only from the Science/Yachts sheets; grid names carry none; when the registry disagrees the maximum is used.
6. Unknown length is a warning, not an error, because most historic vessels lack one.
7. Events (community sail day, campus event, emergency port call, training) occupy the whole berth for the day; Holiday and "Road race - access limited" do not consume capacity.
8. Closures set capacity to zero for their days; a closure in an unlabelled row applies waterfront-wide (`berth_id NULL`) and is reported, not enforced against specific berths.
9. Operational notes (ETA, departs, fueling, fuel truck, delayed, touch and go) are annotations of a booking, never bookings.
10. Pre-2009, consecutive identical names in one row are one stay; a lone cell is a one-day stay; shared fills extend a stay only when the named cell's fill is non-default.
11. A stay ending on the last day of a month and the same vessel starting on day 1 of the next month on the same berth is one stay.
12. The 8YR summary counts vessel-days; the reconciliation reports both definitions.
13. Case-only name variants are the same vessel; names differing by a word are different vessels (synthetic vocabulary is small).
14. Imported history is read-only in the app; new bookings are tagged `source='app'`.

## interview_points
1. How does the double-booking check work exactly? For each day in the requested range I gather every reservation on that berth covering that day (end-inclusive), add the known vessel lengths plus 10 feet of clearance between neighbours, and compare with the berth length; a berth of 75 feet or less holds one vessel regardless. Closures make the capacity zero and events occupy the whole berth. The function is pure and lives in one file, and the audit and the API both call it.
2. Why not simply "one vessel per berth"? Because the data disproves it: a 410-foot pier face holds several vessels end to end and the grids show three or four names on one day. Linear capacity is the constraint the coordinator actually checks by eye today.
3. What did you do when a vessel has no length? The registry covers only a fraction of the 504 vessels, so unknown length is a warning that says "cannot verify", not a block; blocking would make the tool unusable on day one. The report counts these so the facility knows how many lengths to fill in.
4. How did you handle 23 years of changing layouts? I did not hard-code eras. Each month block is found by its header, the day-number row is detected as either the header row or a row of `1, =SUM(..+1)` formulas, berth rows are found by label, and the year always comes from the sheet name. That last rule is what turns "NOVEMBER 2018" in the 2010 sheet into a finding instead of a bug.
5. Pre-2009 stays are not merged cells; how do you know a stay's length? I don't, and the data model says so: every imported stay carries a confidence (`merged`, `repeated`, `fill`, `single`). Repeated names in consecutive columns are one stay; a lone name is one day. The report states what share of stays are inferred.
6. What is the 8YR summary reconciliation and what did it show? I recomputed usage days per berth per year from the grids in two ways (vessel-days and occupied days) and compared with the summary sheet. The summary counts vessel-days, contains berths that the grids of those years do not have, and disagrees with the grids in specific cells; the table lists every delta. The lesson for the client is that the summary was maintained by hand.
7. How do you know the system works? Twelve named unit tests spell out the rule, a fixture workbook with one block per era tests the importer, a golden test pins the counts from the real workbook, and three audit findings were checked by hand against Excel and cited in the README.
8. What would you do next with more time? Enforce rafting as side-by-side capacity using the registry's "will raft" flag, add draft and tide constraints, add arrival/departure times so same-day turnarounds are not conflicts, make imported history editable with an audit trail, and import the Tours log so dock tours appear on the timeline.
